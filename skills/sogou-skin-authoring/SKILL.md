# 搜狗皮肤制作工作流

你手上有一套 `skin_*` 工具。用户不会关心格式细节，**你的职责是把"几张图片"变成"一个能用的皮肤"**，并且在每一步给用户看得见的东西。

## 一、先问清楚三件事，然后立刻给清单

1. **有素材吗？** 有立绘/背景图 → 走 A 路线；纯色或没有素材 → 走 B 路线（占位图先跑通）。
2. **皮肤叫什么名字、作者写谁？**
3. **状态栏要哪些按钮？** 至少 `cn_en`（中/英）。

然后用 `skin_requirements` 拿到完整素材清单，**用中文表格转述给用户**（不要直接把 JSON 丢过去）。清单里要讲清楚：

- 必需：横排候选窗底图、竖排候选窗底图、状态栏底图、中/英图标
- 每个按钮图标都要 **常态 / 悬停 / 按下** 三态；只给一张的话插件会自动推导另外两张
- 图标建议 **20×20**；面板图必须是 **PNG（带透明通道）**
- 引擎只吃 **PNG 和 BMP**。本插件零依赖、不解码 JPEG/WebP/GIF —— 用户给的是 JPG 时要明确告诉他先转 PNG

## 二、建工程

`skin_init(dir, name, author)`。工程目录立刻就有了 `assets/` 和 `preview/`。

如果用户还没准备好素材，**不要干等**：用占位素材先把全流程跑通，给用户看一张预览，他才知道自己要提供什么。默认 `skin_init` 就会生成占位素材。

## 三、扫描用户素材（这一步是你的"眼睛"）

素材放进 `assets/` 后，调 `skin_scan_assets(dir)`。返回的每张图带：

| 字段 | 用途 |
|---|---|
| `width`/`height`/`aspect` | 判断是面板还是图标 |
| `hasAlpha`/`transparentRatio` | 没有 alpha 的图要警惕（JPG 转来的会是全不透明）|
| `dominantHue` | 判断整套素材色调是否统一，决定配色方案 |
| `bbox` | 内容实际占的区域，四周多余空白可以 trim |
| `suggestions` | 插件给的槽位猜测（**只是建议，最终由你判断**）|

**你必须做的判断**（插件猜不出来的）：

- 两张宽图哪张是横排、哪张是竖排？看长宽比 + 内容分布
- 状态栏底图是不是混在图标里了？
- 素材色调跟用户想要的主题一致吗？不一致就走第四步的色相归一
- 图标是不是一张拼图？是的话用 `sheet` 让插件自动切分

把判断结果用 `skin_assign` 落地。**不确定的槽位要问用户，不要瞎猜。**

## 四、细节修复（`skin_repair`）—— 这是 AI 相对普通工具的唯一优势

先跑一次 `skin_assemble` + `skin_preview`，然后用 `read_image` **亲眼看预览图**，再决定修什么。常见问题与处方：

| 预览里看到的问题 | 处方 |
|---|---|
| 图标外面有一圈白底/黑底 | `removeBackground`（色键抠图，配 `tol` 调力度）|
| 图标太小、有大片空白 | `trim` 再 `containFit` 到 20×20 |
| 面板拉伸后边缘撕裂 | 说明九宫格边界不对：把 `nineSlice` 显式传给 `skin_assign`，让可拉伸区域落在纯色带上 |
| 整套素材色调不统一 | `normalizeHue`（把每张图的主导色相搬到同一个目标色相）|
| 图标在底图上糊成一团 | `skin_repair` 的 `outline` 加描边 |
| 拼音串和候选词挤在一起 | 调 `pinyin_marge` / `zhongwen_marge`（格式是 **top,bottom,left,right**）|

**验收标准**：候选窗的四个圆角不变形、纯色带拉伸处看不出接缝、图标在状态栏底图上清晰可辨。

## 五、预览精修闭环（这是本技能的核心，别跳步）

`skin_preview` 产出**三张图，三张都必须用 `read_image` 亲眼看**：

| 图 | 看什么 |
|---|---|
| `preview/preview.png` | **整体观感**：配色是否协调、立绘位置是否合适、文字会不会被压住 |
| `preview/assets.png` | **素材是否齐整**：尺寸是否统一、有没有多余白边、三态是否都生成了 |
| `preview/stretch.png` | **九宫格是否选对**：同一张底图被拉到 340/560/860/1240 四个宽度，边角变形会在这里暴露 |

### 闭环流程（每轮都要走完）

1. `skin_preview` 出图
2. **三张图逐一 `read_image`**，不要只看第一张就下结论
3. 对着下面的眼睛看什么/怎么改表，列出**具体问题**（不要笼统说"看起来还行"）
4. 把问题翻译成 `skin_repair`（改图）或 `skin_assign`（改槽位/九宫格/配色）的调用
5. **回到第 1 步**，直到 `skin_validate` 无 error、`stretch.png` 各宽度下尖角形状一致
6. 把最终三张图给用户看，说清楚这次改了什么、还剩什么

### 逐轮体检表

| 在预览里看到 | 怎么改 |
|---|---|
| **候选窗拉宽后左/右尖角变形** | `skin_assign` 里显式传 `nineSlice: {left,right}`——值取装饰的实际像素宽度。**注意 `layout_horizontal = mode,left,right`，第一个数是 mode，别把 0 当成 left**（这个坑真实发生过）|
| 装配警告里出现"边宽 = 0 但该侧有内容" | 同上，把那条边宽改成正数 |
| 状态栏图标糊在底图上 | `skin_repair` 的 `outline` 加描边，或用 `removeBackground` 抠底 |
| 图标大小不一 | `skin_repair` 的 `containFit` 统一到 20×20 |
| 整套色调不统一 | `normalizeHue` 把每张图的主导色相搬到同一个目标色相 |
| 拼音串压住候选词 | 调 `pinyin_marge` / `zhongwen_marge`（**top,bottom,left,right**）|
| 立绘被裁掉 / 位置怪 | `skin_repair` 的 `containFit` 调整，或换槽位明确用 `nineSlice` 把立绘排除出可拉伸区 |

**验收标准**：`skin_validate` 0 error；`stretch.png` 里四个宽度的尖角形状一致、中段无接缝；
`preview.png` 整体协调；`assets.png` 图标尺寸统一。

预览图的表达限制（要如实告诉用户，不要假装是最终效果）：
- 插件不带中文字库，候选词用**词块**示意，标题里的汉字显示为"豆腐块"
- 拼音串用自带点阵字模真实绘制，字形比真实输入法粗糙

## 五·五、画皮肤的正确姿势（设计工作流，按顺序做，每步都要看图）

> 这一节来自一次真实的设计返工。教训写在最前面：**不要连着改几版再看结果**。
> 我曾经连改三版预览图排版都没看一眼，最后交出去一张标签错位、区域重叠的废图。
> **每完成一个哪怕很小的步骤，就用 `read_image` 看一眼，不符合预期立刻返工。**

### 第 0 步：先解剖一个成熟皮肤，别急着画

拿 `skin_unpack` 解开一个真实皮肤，逐张看图，把结构写下来。以「雷电将军」为例：

| 部件 | 结构 |
|---|---|
| `bar.png` 122×122 | **以刀为中心**，刀斜置；淡紫羽翼形底；图标排在顶部 `y=1` 一行 |
| `skin1.png` 650×258 | **头** x0..120（白色 `<` 箭头 + 两根白条）／**中** 淡紫渐变条+散景／**尾** 立绘 |
| `skin2.png` 522×428 | **头** 顶部白条／**中** 大块淡紫渐变面板／**尾** 右下立绘 |
| 三张拉伸条 | 极简白色胶囊 + 1px 灰边框 |

两条最容易做反的事：
1. **雷电将军是「浅底深字」**（淡紫条 + 蓝紫文字）。做之前先确认底色明暗，再决定字色，别默认深底浅字。
2. **状态栏不是一条横杠**。玩家皮肤基本都是「以某个图案为中心」的方块，尺寸跟参考皮肤一致。

### 第 1 步：定配色与底色（先定这个，后面全依赖它）

从用户素材里采样，整理成一套有明暗层次的色板：深 / 底 / 主 / 亮 / 浅 / 极浅 / 金 / 墨。
写成代码里的常量，后面所有图层都从这里取色——**不要在任何地方硬编码颜色**，否则改主题要满文件找。

### 第 2 步：状态栏（桌面图标）

- 尺寸对齐参考皮肤（雷电将军是 122×122）
- **中心图案**（Q 版 / 徽记 / 主视觉）放正中，下面垫一个圆盘 + 柔光，让它「浮」起来而不是贴上去
- **功能图标环绕布置**，不要排成一列：上 / 左 / 右 / 左下 / 右下 / 下，距中心「不要太远也不要太近」
- 描边**沿底座轮廓走**（用 `outlineAlpha`），不是画个圆角方框

### 第 3 步：候选窗 = 头 + 中 + 尾（三段式，这是核心）

| 段 | 要求 | 反例 |
|---|---|---|
| **头** | 简洁干净，用**有限的花纹和结构**构造。收口、云头、两道金线就够了 | 堆一堆装饰 |
| **中** | **纯渐变**。这里是打字的地方，不宜太深太花哨。**必须没有任何花纹**，否则拉长时会被抹开 | 放散景、粒子、图案 |
| **尾** | 立绘 + 复杂纹样都放这里 | —— |

中段的「纯」是可以量化的：横向相邻像素差 >4 的比例应该是 **0%**。装配器会自检。

### 第 4 步：勾边要沿着图案边界

用 `draw.js` 的 `outlineAlpha`（形态学膨胀/腐蚀），它会贴着真实轮廓走。
颜色取**整体配色里偏深的那一档**，不要用纯黑。

> ⚠️ **只对「主体」那一层勾边**，不要对合成后的整张图勾。
> 否则半透明的光晕、渐变尾巴都会被框成硬边矩形——我踩过这个坑。

### 第 5 步：逐张自查清单

每做完一个部件，`read_image` 看，逐条过：

- [ ] 形状对不对？有没有变成意料之外的样子（比如想做云头结果成了楔形）
- [ ] 有没有不该出现的硬边矩形？（通常是某层 alpha 没处理好，或勾边勾错了层）
- [ ] 明暗够不够？扁平 = 缺竖向明暗渐变
- [ ] 配色和谐吗？新加的色是不是都在色板里
- [ ] 中段是不是真的「纯」？（纯渐变，没有花纹）
- [ ] 文字离边缘的距离够不够？（远景看会不会挤）

### 可用的绘图原语（`src/image/draw.js`）

| 函数 | 用途 |
|---|---|
| `line` / `curve` | 抗锯齿线段 / 贝塞尔曲线（Catmull-Rom）|
| `circle` / `roundRect` | 抗锯齿圆、圆环、圆角矩形（`ring` 参数描边）|
| `gradientStops` / `radialGradient` | 多段线性渐变 / 径向渐变 |
| `glow` / `innerGlow` | 外发光 / 内发光 |
| `grain` | 颗粒噪点，去掉「塑料感」|
| `blur` / `blurGaussian` / `dropShadow` | 盒式模糊 / 近似高斯 / 投影 |
| `outlineAlpha` | **沿轮廓**勾边（`inside:true` 为向内）|

> 两个已知陷阱：
> 1. `blend` 遇到 `alpha=0` 会直接跳过 —— **不能用它「擦除」**，要直接改 `data[i+3]`。
> 2. 蒙版裁切要**相乘**（`dst.a *= mask.a`），不是再叠一层。

## 五·六、九宫格退化 —— 「整张底图被压扁拉长」的唯一根因

这是最容易踩、后果最严重、又最难自己发现的坑。**如果你只读一节，读这节。**

### 机制

引擎拿到一个 W×H 的窗口，要按九宫格把底图铺进去。一旦：

```
   left + right >= W      或      top + bottom >= H
```

九宫格就**不成立**。这时引擎没有别的选择，只能把**整张底图硬缩放到 W×H** ——
立绘被压扁、文字跑位、上下两排错乱，全都是这一个原因。

### 真实案例（我踩的）

克隆「雷电将军」时，我把作者的 `layout_vertical = 0,33,11` 擅自"优化"成 `0,168,12`。
纵向内缩之和从 44 涨到 **180**。只要引擎给的窗口高度小于 180，九宫格立刻退化 → 严重纵向拉伸。

**教训：克隆真实皮肤时，`layout_*` 必须原样保留。** 那是作者在编辑器里拉过导引线的结果，
你没有依据去改它。

### 正确做法：只在真正会变化的那根轴上设防

| 段落 | 会怎么变 | 该给内缩的轴 | 另一轴 |
|---|---|---|---|
| `Scheme_H1` 横排候选窗 | 打字变长 → **只变宽** | `layout_horizontal` | `layout_vertical = 0,0,1` |
| `Scheme_V1` 竖排候选窗 | 候选变多 → **只变高** | `layout_vertical` | `layout_horizontal = 0,0,1` |

给不会变的那根轴设内缩**没有任何好处**（尺寸不变，内缩用不上），却会让九宫格在
"引擎给出一个小于内缩之和的尺寸"时直接退化。所以那一轴一律给 `0,0,1`。

### 参照值（7 个真实皮肤的实测）

| 皮肤 | layout_horizontal | layout_vertical |
|---|---|---|
| 官方内置 ×4 | 4,4 / 9,9 / 20,20 / 15,16 | 同左（都很小）|
| 雷电将军影宝 H1 | 100,300 | **33,11** |
| 雷电将军影宝 V1 | 80,300 | **31,1** |
| 原神—雷电将军 H1 | 123,295 | **0,1** |

### 自动体检（不需要真机）

1. **`skin_validate`** 会在多组典型窗口尺寸下跑退化探测，退化直接报 error；
2. **`skin_preview`** 产出的 **`render.png`** 是按引擎模型真渲染出来的，
   出现 `!!` 开头的提示就说明退化了。

> **不要只看 `preview.png`。** 那是我自己画的设计示意图，**看不出退化**；
> 只有 `render.png` 与 `stretch.png` 才走真实的九宫格路径。

## 五·七、引擎的配置类结构（从 UIPlugin.dll 的 RTTI 里读出来的）

命名空间 `SkinConfigFile`，这解释了 ini 里每个键最终被解析成什么类型：

| 类 | 对应 ini 写法 |
|---|---|
| `SkinInt / SkinBool / SkinStr / SkinColor` | 标量 |
| `SkinPos` | `<按钮>_pos=x,y` |
| `SkinAlign / SkinAlignEx` | 浮层对齐（那个十元组）|
| `SkinSeperator` | `separator=颜色,左,右` |
| `SkinToLeftRight` | `to_left_right`（样本皮肤里从未出现）|
| `SkinImage / SkinSplit / SkinFlashs` | 图像相关 |
| `SkinBtn / SkinBtnUi / SkinBtnComponent / SkinBtnsComponent / SkinBtnsCustom` | 按钮 |

引擎解析多整数用的格式串是 `%d,%d,%d,%d` 与 `%d,%d,%d,%d,%d,%d`。

**样本皮肤里没出现、但引擎确实认识**的键（已补进词表）：

`ninehint_color`、`clear_edge`、`widget_cnt`、`click_color`、
`click_color_enable`、`seperatorui`、`to_left_right`、`pic_preview`、`webpage_url`。

还有一批按钮名：`handinput`、`news`、`emotion`、`multiscreeninput`、
`translate`、`screencapture`、`inputassist`、`writespirit`、
`gamecenter`、`ichat`、`voice`、`picface`。

## 五·八、候选窗里是【上下两排文字】—— 位置模型（真机标定）

**这是我在这一整轮里栽得最久的坑：我一直以为横排候选窗里只有一排文字。**

实际上每一张 Sogou 官方渲染的预览图里都是两排：

```
  ┌──────────────────────────────────────┬──────────┐
  │ 搜狗PINYIN            ← 拼音行        │          │
  │ 1.拼音 2.品 3.频 4.拼 5.贫 ◀ ▶  ← 候选行│  立绘    │
  └──────────────────────────────────────┴──────────┘
```

### 标定方法

Sogou 自己会把在线皮肤的预览图缓存在
`C:\Users\<用户>\AppData\LocalLow\SogouYS\SkinPreview\*.png`。
**那是真渲染器输出，是最好的基准素材** —— 比任何猜测都可靠。量了 10 张，得到：

| 皮肤 | 文字面板高 | 拼音行（相对面板顶）| 候选行（相对面板顶）|
|---|---|---|---|
| 苍翠欲滴 | 85 | +25 | +49 |
| 玩家投稿-貂蝉 | 77 | +14 | +40 |
| 金蝉·渡世行者 | 77 | +15 | +41 |
| 去冲浪 | 85 | +27 | +50 |
| 起床啦 | 81 | +18 | +43 |

再用两个第三方皮肤的 ini 值反推，两条规律对得上：

```
拼音行 y = pinyin_marge[0]                                  ← 窗口内的【绝对】y
候选行 y = pinyin_marge[0] + font_size + zhongwen_marge[0]
```

校验：

| 皮肤 | 底图 | 面板顶 | pinyin_marge[0] | 算出拼音行 | 算出候选行 | 真机实测 |
|---|---|---|---|---|---|---|
| 雷电将军影宝 | 650x258 | 173 | 195 | **+22** ✓ | 195+16+7=218 → **+45** ✓ | +15..27 / +40..51 |
| 原神—雷电将军 | 449x182 | 88 | 104 | **+16** ✓ | 104+16+8=128 → **+40** ✓ | 同上 |

**两个皮肤两排全部落在实测区间内。**

### 推论：窗口尺寸 ≈ 底图原始尺寸

`pinyin_marge[0]` 是绝对 y（雷电将军 195、原神 104），这两个值都落在各自底图的文字面板里 ——
**只有窗口高 ≈ 底图高时才成立**。所以别再随手定一个「看起来合理」的窗口尺寸去渲染预览，
那样文字会直接跑到窗口外面，预览毫无参考价值。`render.js` 已改成默认取底图原始尺寸。

### 给新皮肤定 marge 的配方

设文字面板（底图里那条扁而宽的实心带）顶为 `P`，则照抄真实皮肤的规律：

```
pinyin_marge   = [P + 20, 4, 左留白, 右留白]     ← 拼音行落 P+20 附近
zhongwen_marge = [6, 5, 左留白2, 右留白2]        ← 候选行 = P+20+font_size+6
```

## 五·十、窗口尺寸与 layout 模式（用真机渲染标定的）

### 窗口尺寸 = 400 × 底图原始高度

从 `SkinRecommend.ini` 里拿到了皮肤下载地址和**每个段落的官方预览图**，
下载「皮肤 + 官方渲染图」配对，量出来：

| 皮肤 | 底图 | 官方 previewH1 | 横向缩放 | 纵向缩放 |
|---|---|---|---|---|
| 苍翠欲滴 | 120x87 | 400x87 | 3.33 | **1.000** |
| 王者荣耀貂蝉 | 315x123 | 400x123 | 1.27 | **1.000** |
| 小白熊 | 297x143 | 400x143 | 1.35 | **1.000** |

**宽度固定拉到 400，高度永远是原始高度、绝不缩放。**
拿我的 `render.js` 按这个尺寸渲染，貂蝉与小白熊**和官方渲染几乎逐像素一致**。

> 复刻/克隆的皮肤，底图高度就是作者设计的目标窗口高度 —— **不要自己加高**。

### `layout_` 第一个数字是模式，不是左边距

| 值 | 含义 |
|---|---|
| `0,L,R` | 拉伸（stretch）|
| `1,L,R` | **平铺（tile）**|

样本里两种都有，例如苍翠欲滴用的就是 `1,30,95`。

### 内缩之和可以超过底图尺寸

苍翠欲滴的 `layout_horizontal=1,30,95`，30+95=125 > 底图宽 120。
**引擎是夹住处理的，不能判定为退化。** 我之前在这里判错，把一张正常皮肤渲染成了废图。
正确做法：先把内缩夹到源图尺寸内（`L=min(L,w-1)`，`R=min(R,w-1-L)`），再判断退化。

## 五·十一、真机实测数据（唯一一次拿到真实渲染）

用一个自己创建的 WinForms 窗口 + `SendKeys` 驱动真实输入法，截屏后做连通域测量，拿到了硬数据：

| 项 | 值 |
|---|---|
| 屏幕 DPI | 168（缩放 1.75x）|
| 候选窗包围盒 | 805 × 454 物理像素 = **460 × 259 逻辑像素** |
| 对应底图 `skin1.png` | 650 × 258 |
| **纵向** | 259 vs 258 → **1:1，完全没有纵向缩放** |
| 横向 | 650 → 460，按内容宽度收缩；`L+R=400 < 460` 成立，九宫格正常 |

**结论：窗口高度 = 底图高度，纵向永不缩放。** 这和从官方预览图（400 × 底图高）推出的规律一致。

### 复现方法（不需要人工操作）

1. 起一个 `System.Windows.Forms.Form`（含 `TextBox`，`TopMost`），标题用**纯 ASCII**
   —— .ps1 若含中文且无 BOM，PowerShell 会按 ANSI 读，窗口标题变乱码，`AppActivate` 就找不到它；
2. 父进程用 `Interaction.AppActivate(标题)` 抢焦点（**用标题，不要用进程 ID**，用 ID 会抛异常）；
3. 子进程里 `Add_Activated({ $t.Select(); $t.Focus() })` —— 只在 `Add_Shown` 里 Focus 不够，按键会丢；
4. `SendKeys.SendWait("nihao")` 触发候选窗，`ImageGrab` 截屏；
5. 测量时**别用"亮像素"做连通域**——会把探测窗的白色文本框一起吞进来。
   用**皮肤特征色**（如 `#c9b8e8`）做种子填充，才能框出候选窗。

---

### 踩坑记录：换皮肤文件骗不过引擎

想测另一个皮肤，最直接的想法是"把活动皮肤的文件覆盖掉"。**试过了，不生效** ——
把 `AllSkin\复刻-雷电将军.ssf` 换成闲云的内容、并杀掉所有 Sogou 相关进程后，
引擎渲染出来的**仍然是原来那张艺术图**。说明皮肤数据有更持久的缓存（很可能在 `skin_v3.dat` 里）。

**要测另一个皮肤，只能真的在输入法里把皮肤切过去**，或者直接问用户当前选的是哪个。

### 测量时别用「亮像素」或「近似色」做连通域

两次翻车：

1. 用「亮像素」当掩码 → 把自己开的探测窗（白色文本框）一起吞进来了；
2. 用「接近主色」当掩码 → 在浏览器页面上测时，页面本身的相近色也被吞进来，量出 2520x1358 这种荒唐数字。

**可靠做法：把候选窗悬在纯深色区域上**（把探测窗做小、放到左上角，让候选窗右侧落在桌面上），
再用皮肤特征色取种子。或者干脆做**帧间差分**（有候选窗 vs 没候选窗两张图相减）。

---

### 第二次真机实测（帧间差分法，最可靠）

方法：候选窗**显示时**截一张、**按 Esc 关掉后**再截一张，两张相减 —— 差异区域就是候选窗，
不受背景颜色干扰。这是目前最可靠的做法。

复刻（skin1.png 650×258）两次实测：

| 次数 | 窗口（物理）| 窗口（逻辑）| 纵向 / 底图高 258 |
|---|---|---|---|
| 第 1 次 | 805 × 454 | 460 × 259 | **1.004** |
| 第 2 次 | ~1130 × 440 | 646 × 251 | **0.973** |

**两次纵向都是 ~1:1。宽度随候选数量变化（460 / 646），高度不变。**
结论再次确认：**窗口高度 = 底图高度，纵向永不缩放。**

### 又一条死路：改 env.ini 的 ActiveSkinName 也切不了皮肤

`C:\Users\<用户>\AppData\LocalLow\SogouYS\env.ini`（UTF-16LE）里有 `ActiveSkinName=皮肤名`，
看着就是"当前皮肤"。改掉它 + 杀掉全部 Sogou 进程 + 重启，**渲染出来的仍然是原来那张艺术图**。

加上之前试过的"直接覆盖 AllSkin 里的 .ssf"也不生效 —— 可以断定**皮肤数据被缓存在 `skin_v3.dat` 之类的持久化文件里**，
光换文件或换名字都骗不过引擎。

**要测另一个皮肤，只能让用户在输入法里真的切过去。** 别再在这上面绕了。

## 五·十二、候选条必须【贴到图片底边】（否则多行候选会掉到桌面上）

**症状**：候选词超过一行时，第二行往后的词落在黑色桌面上，底下没有背景板。

**根因**：Sogou 把候选词依次往下排。如果底图里条子下方是透明的，那些行就没有背景。

| | 复刻（正常）| 闲云（出事）|
|---|---|---|
| 底图 | 650x258 | 700x236 |
| 条子纵向位置 | y 168..246 | y **156..208** |
| 条子占底图底部 | **95%**（下沿几乎贴底）| 只到中段，底下空 28px |
| 结果 | 窗口变高时条子颜色自然铺下去 | 列表掉到桌面上 |

**修法**：把条子的下沿做到图片底边（`BAR_H` 从 52 改成 80，`BAR_Y=156` 不变），
并把 `layout_vertical` 改成 `0,156,0` —— 只让条子那一段参与纵向拉伸。

实测效果：玉色纵向覆盖 **51 逻辑像素 → 206 逻辑像素**，多行候选全部有背景。

### 设计期就该检查的三条（写进 validate）

1. **条子下沿 == 图片高度**（或至少距底 ≤ 4px）；
2. 条子下方那一段在【中间 x 范围】内必须是不透明的（列表就排在那里）；
3. `layout_vertical` 的 `top` 应等于条子上沿的 y，`bottom` 应为 0。

## 五·十三、⚠️ 改完皮肤必须【先确认引擎读了新文件】

## 五·十四、精修期的四条硬教训（都是血换的）

### 1. 看图看不出所以然时，去量一个数

有一次我看状态栏按钮"觉得圆角被切了"，换角度又看了两遍，还是说不清。
最后打印了一列 alpha 值，当场定位到**完全不同的、更严重的 bug**：

```
中列 (x=10) 逐行 alpha:
  y 0..9  = 16 16 16 16 ...   ← 上半块几乎全透明！
  y 10..19= 200 200 ...       ← 下半块才正常
```

**"看图觉得不对但说不清"的时候，下一步是量数，不是换个角度再看一遍图。**

### 2. `placeholder.js` 里的 `roundRect` 是【覆盖写】，不是混合

我加了一行"上半部高光"：

```
roundRect(r, 0, 0, W, H/2, 5, [255, 255, 255, 16]);   // 看着像叠 6% 白
```

结果它**把按钮上半块整个替换成了 alpha=16 的白** —— 不是加高光，是擦除。
凡是"叠一层淡色"的想法，先确认目标函数是 blend 还是 overwrite。
（同一个文件里 `raster.js` 的 API 是混合的，这个局部 `roundRect` 不是。）

### 3. 校验规则必须拿【已知正常】的样本反测

我加过两条规则，**两条都在正常皮肤上误报**：

| 规则 | 误报对象 | 原因 |
|---|---|---|
| 九宫格退化探测 | 复刻-雷电将军 | 测试尺寸填的是 26x32 这种**根本不存在的窗口高度**（真机实测横排窗高约等于底图高）|
| 条子未贴底 | 复刻-雷电将军 | 只看"图片最后一行透不透"，**没考虑 `layout_vertical` 的固定区**能兜住 |

**一条会在正常样本上报错的规则，比没有规则更糟** —— 它会驱使你去改坏一张本来正常的皮肤。

落地做法：每条规则上线前，先跑已知正常的皮肤，**必须零告警**；做不到就降级成"提示"，
并把**已知反例写进提示文案里**，免得后人照着去改。

### 4. 一行读不出内容的警告，会掩盖一条一直是错的警告

`[面板] undefined` 这行喊了七八轮，因为读不出内容所以没人管。
修好文案格式后一看 —— **它一直在报一张验证过、完全正常的皮肤。**

**修不动的东西不等于没问题，可能只是坏得看不出在说什么。**
任何 `undefined` / `NaN` / 空字符串出现在输出里，都当成 bug 立刻修，不要"回头再说"。

## 六·五、装到用户机器上

`skin_install(file)` 会自动探测本机搜狗输入法的皮肤目录（医生版 / 标准版 / 多版本子目录都支持），
把 .ssf 复制进去。**先跑一次 `dryRun: true` 给用户看会写到哪**，确认后再实装。
`skin_list_installed()` 用来确认装进去了没有。

注意：皮肤目录是**输入法启动时扫描**的。如果用户没在皮肤列表里看到新皮肤，
让他重启一下输入法（或切换一次皮肤），不要声称“装失败了”。

## 七、必须记住的格式陷阱

1. **颜色是 `0xBBGGRR`（Windows COLORREF），不是 RGB。** 两个真实样本实测确认。写进 Skin.ini 前一定要换算，否则红蓝颠倒。
2. **三态后缀 1/2/3 = 常态/悬停/按下**，由 Skin.ini 里的 `cn_en` / `cn_en_hover` / `cn_en_down` 显式声明。
3. **`layout_horizontal = 模式,左,右`、`layout_vertical = 模式,上,下`** 是九宫格里"不可拉伸"的边宽。搞错了拉伸就会撕裂。
4. **`*_marge` 四元组顺序是 top,bottom,left,right**（三个独立皮肤交叉验证确认）。
   判据：第 2 位在三个皮肤上恒定很小（2/4/5）= 底边距；第 4 位在带立绘的皮肤上很大（200/270）= 给立绘腾的地方。
   若按 left,top,right,bottom 读会得出"底边距 200"，在一张 258px 高的图上是荒谬的。
5. 状态栏按钮是**可选**的：不给某按钮的图标，它就不出现在状态栏上。
6. 图标 **BMP 是 24 位无透明通道**的，透明只能靠色键；能用 PNG 就优先 PNG。
7. **候选窗内的浮层按钮**（翻页 ↑↓ / 展开更多候选 / 自定义）不用 `_pos`，而是用 **10 元组的 `_align`**。
   这个十元组只被部分逆向（`a[2]/a[3]` 是按钮中心偏移、`a[7]/a[8]` 是布局常量）。
   **不要自己编数值** —— 先调 `skin_overlay_presets` 拿官方预设，或从用户已有的皮肤里抄一组。
   插件会把你给的 align 原样写入，不做任何推导。
