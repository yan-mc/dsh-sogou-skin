# 经验教训

这份文档记录本项目开发过程中**真实踩过的坑**。每一条都对应一次实际的返工，
不是泛泛而谈的建议。按"如果我早知道，能省多少事"排序。

---

## 一、验证类：怎么确认自己真的修好了

### 1. 「改了文件」≠「引擎用了新文件」

改了皮肤文件、杀了进程、重启，渲染结果**一个像素都不变**。连续四轮卡在这里。

根因：搜狗把皮肤数据缓存在
`%%LOCALAPPDATA%%Low\SogouYS\skin_v3.dat`。
只改 `AllSkin` 里的 `.ssf`、改 `env.ini` 的 `ActiveSkinName`、杀进程、重启，**都不会让它重读文件**。

**唯一有效的办法：删掉 `skin_v3.dat`，再重启输入法。**

**教训**：改完东西，**先用一个"改动的直接、可量化的后果"确认生效了，再评估效果**。
我当时用的判据是"条子高度应该从 51 逻辑像素变成 80"——一量就知道文件加载没有。
**不要用"画面看起来变了没有"当判据。**

### 2. 看图看不出所以然时，去量一个数

我看状态栏按钮"觉得圆角被切了"，换角度又看了两遍，还是说不清。
最后打印了一列 alpha 值，当场定位到**完全不同的、更严重的 bug**：

```
中列 (x=10) 逐行 alpha:
  y 0..9  = 16 16 16 16 ...   ← 上半块几乎全透明！
  y 10..19= 200 200 ...       ← 下半块才正常
```

**"看图觉得不对但说不清"的时候，下一步是量数，不是换个角度再看一遍图。**

### 3. 一行读不出内容的警告，会掩盖一条一直是错的警告

`[面板] undefined` 这行喊了七八轮，因为读不出内容所以没人管。
修好文案格式后一看 —— **它一直在报一张经过真机验证、完全正常的皮肤。**

**修不动的东西不等于没问题，可能只是坏得看不出在说什么。**
任何 `undefined` / `NaN` / 空字符串出现在输出里，都当成 bug 立刻修。

## 二、校验器类：工具也会骗你

### 4. 校验规则必须拿【已知正常】的样本反测

我加过两条规则，**两条都在正常皮肤上误报**：

| 规则 | 误报对象 | 原因 |
|---|---|---|
| 九宫格退化探测 | 复刻-雷电将军 | 测试尺寸填的是 26x32 这种**根本不存在的窗口高度** |
| 条子未贴底 | 复刻-雷电将军 | 只看"图片最后一行透不透"，**没考虑 `layout_vertical` 的固定区**能兜住 |

**一条会在正常样本上报错的规则，比没有规则更糟** —— 它会驱使你去改坏一张本来正常的皮肤。

**落地做法**：每条规则上线前先跑已知正常的样本，**必须零告警**；
做不到就降级成"提示"，并把**已知反例写进提示文案里**。

### 5. 【真机实测】才是唯一的事实来源

我基于"官方预览图 + 第三方皮肤 ini"反推出了一套引擎模型，
用它渲染出的结果**看起来非常合理** —— 但它是错的。

后来用真机截图量出了硬数据：

| 项 | 值 |
|---|---|
| 屏幕 DPI | 168（缩放 1.75x） |
| 横排候选窗包围盒 | 805x454 物理 = **460x259 逻辑像素** |
| 对应底图 | 650x258 |
| **纵向** | 259 vs 258 → **1:1，纵向永不缩放** |

**模型再自洽，也只是假设。** 有真机可测的时候，先测。

## 三、改动类：什么时候该停手

### 6. 克隆/复刻时，配置必须逐字一致

我"复刻"雷电将军时自作主张改了一堆配置。逐字段对比原版，**81 个键里有 48 个不一致**：

| 我改了什么 | 原版 | 被我改成 |
|---|---|---|
| 给四个段落加 `layered=1` | 没有这个键 | 全加了 |
| 给状态栏加 `pic_mask` | 没有 | 加了 |
| 把 `Scheme_H2`/`V2` 的 layout 清零 | `0,2,25` | `0,0,0` ← **完全退化** |
| 改 `Scheme_V1` 的 layout | `0,80,300` | `0,0,1` |
| 改 `anchor` | `100,130` | `50,0` |

**用户报的"严重纵向拉伸"就是这么来的。**
其中 `layout_vertical` 从作者标定的 `0,33,11` 被我改成 `0,168,12`，
内缩之和从 44 涨到 **180** —— 只要引擎给的窗口高度小于 180，九宫格就退化，引擎只能整图缩放。

**正确做法**：原版 Skin.ini 逐字照抄，只改 `skin_name` / `skin_version` /
`skin_author` / `skin_email` / `skin_time` / `skin_info` 这六个身份字段。
改完再逐字段对比一次：**除身份字段外必须零差异**。

### 7. 九宫格退化 —— 「整张底图被压扁拉长」的唯一根因

引擎要把底图按九宫格铺进一个 W×H 的窗口。**只要**：

```
  left + right > W      或      top + bottom > H
```

**九宫格就不成立**，引擎只能把**整张底图硬缩放到 W×H** —— 立绘被压扁、文字跑位、上下两排错乱，全是这一个原因。

**关键**：只在**真正会变化的那根轴**上设内缩。

| 段落 | 会怎么变 | 该设防的轴 | 另一轴 |
|---|---|---|---|
| 横排候选窗 | 打字变长 → **只变宽** | `layout_horizontal` | `layout_vertical = 0,0,1` |
| 竖排候选窗 | 候选变多 → **只变高** | `layout_vertical` | `layout_horizontal = 0,0,1` |

给不变的那根轴设内缩**没有任何好处**，却会让九宫格在窗口偏小时直接退化。

### 8. 「觉得还能更好」是最大的风险源

我因为"觉得还能更好"改坏过三样东西：

- 把作者的 `layout_vertical` 从 `0,33,11` 改成 `0,168,12` → 整张图被压扁（见第 6 条）
- 勾边做**两遍**模糊 → 本该是"勾边"，糊成了 3px 发光
- 加"上半部高光" → 见第 9 条，把按钮上半块擦掉了

**有一条是有价值的**：给候选条头部做 3 倍放大检查后，我判定"只有 1~2 像素级的瑕疵，实际显示尺寸下看不见"，
**决定不改**。在有多项"越改越坏"记录的情况下，**"确认不用改"也是进展**。

### 9. 先确认目标函数是"混合"还是"覆盖"

`src/skin/placeholder.js` 里有个局部 `roundRect`，它是**覆盖写**。
我写了这么一行"上半部高光"：

```
roundRect(r, 0, 0, W, H/2, 5, [255, 255, 255, 16]);   // 看着像叠 6% 白
```

结果它**把按钮上半块整个替换成了 alpha=16 的白** —— 不是加高光，是擦除。
（同一个项目里 `raster.js` 的 API 是混合的，只有这个局部函数不是。）

**凡是"叠一层淡色"的想法，先确认目标函数的行为。**

## 四、设计类：皮肤本身的规律

### 10. 候选窗里是【上下两排】文字

我一直以为横排候选窗里只有一排文字。实际上每一张搜狗官方渲染的预览图里都是两排：

```
  ┌──────────────────────────────────────┬──────────┐
  │ 搜狗PINYIN            ← 拼音行        │          │
  │ 1.拼音 2.品 3.频 4.拼 5.贫 ◀ ▶  ← 候选行│  立绘    │
  └──────────────────────────────────────┴──────────┘
```

位置公式（用官方预览图 + 两个真实皮肤反推，并验证）：

```
拼音行 y = pinyin_marge[0]                                  ← 窗口内的【绝对】y
候选行 y = pinyin_marge[0] + font_size + zhongwen_marge[0]
```

校验：雷电将军 195+16+7=218（真机 213..224）；原神 104+16+8=128（真机 128..139）。

### 11. 候选条必须【贴到图片底边】

**症状**：候选词超过一行时，第二行往后的词落在黑色桌面上，底下没有背景板。

**根因**：候选词依次往下排。如果底图里条子下方是透明的，那些行就没有背景。

| | 正常 | 出事 |
|---|---|---|
| 条子纵向位置 | 下沿几乎贴底 | 只到中段，底下留空 |
| 结果 | 窗口变高时条子颜色自然铺下去 | 列表掉到桌面上 |

**修法**：把条子的下沿做到图片底边，并把 `layout_vertical` 改成 `<条子上沿 y>,0` ——
只让条子那一段参与纵向拉伸。

实测效果：玉色纵向覆盖 **51 逻辑像素 → 206 逻辑像素**。

### 12. 勾边要沿着图案边界，颜色取"整体配色里稍深一档"

**不要用近黑。** 我所有勾边原本都用 `ink = [12,42,47]`，
**在黑底上完全隐形，在白底上就是一道黑边**。

而我在黑底上测了整整十几轮，一直没发现 —— 直到用户提醒"你这个玩意在白底的地方会出现黑边"。

**修法**：`ink` 从 `[12,42,47]` 改成 `[26,104,110]`（深青玉），透明度也降下来。

**并且**：`skin_preview` 现在每次都产出 `bgcheck.png` ——
**把底图同时铺在白底和黑底上并排显示**。这种事不该靠人记得。

### 13. 装饰绝不能进入可拉伸中段

中段是打字的地方、要被无限拉伸，**任何图案进去都会被拉变形**。
所有装饰（云纹、光点、流线）都限制在头部（x<210）和尾部（x>470）。

**这条写成硬约束，每次加装饰都要检查。**

### 14. 形态学膨胀得到的是二值边缘，放大看是阶梯状的

`outlineAlpha` 原本用 3x3 结构元逐轮膨胀，每像素非 0 即 1，**没有过渡**。
4 倍放大一眼就能看出轮廓是锯齿。

**修法**：先收集成覆盖度图，做**一遍** 3x3 盒式模糊再混合。

**注意是一遍**：两遍会把 2px 的边糊成 3px 的光晕，看着像发光不像勾边。

### 15. 头/中段交界处会留下一条"截断的线"

头部渐变以 `light(168,228,205)` 结尾，中段以 `pale(222,248,236)` 开头，
**差了 30 多**，交界处 x=118→120 出现 53~64 的颜色跳变 —— 就是用户看到的那条竖线。

**修法**：让头部渐变收在 `pale`，正好接上中段的起点。
**验证：跳变 53~64 → 5~9。**

## 五、流程类：一条能省最多时间的建议

**每一小步做完都看图，而且要在白底和黑底各看一次。**

这条是整个项目里最省时间的一条。上面第 9、12、14、15 条，
**每一条都是"看一眼就能发现、不看就要多花好几轮"的问题**。

配套的三条具体做法：

1. **预览器要自动产出白底对照图**（`bgcheck.png`），别靠人记得；
2. **判据要量化**（"条子高度应从 51 变 80"），不要用"看起来对不对"；
3. **不确定就说不确定** —— 我有一轮明确写了"上面那排按钮的圆角我不确定是不是还被切着"，
   下一轮量了 alpha 才发现真正的问题是"上半块全透明"。**含糊的判断会误导后续。**

## 六、交付类：整理成开源项目时才暴露的问题

这一节是项目基本做完、准备开源时，重新逐项检查才发现的。
共同点是：**代码本身没坏，坏的是"它给别人看的样子"**。

### 16. 整份 `process.exit(0)` 的测试，退出码再好看也没用

项目里有 14 个测试。它们的判据是 `process.exitCode`，CI 里看退出码 —— **全绿**。

但把硬编码的本机路径换成"缺数据就跳过"之后，真相是：

```
真跑断言的  6 个
缺数据跳过的 8 个   ← 其中好几份是整份 exit(0)
```

**"8 个测试通过"和"8 个测试什么都没做"在退出码上完全一样。**

其中 `container.test.mjs` 尤其讽刺：它守的是三代容器的读写正确性，
是项目最核心的能力之一 —— 而它在干净 checkout 里**一条断言都没跑**。

**修法**：让测试**自己造数据**。用程序化占位素材生成一份皮肤，
再对自己的产物做断言。改完之后真跑数从 6 涨到 13，只剩
`compare_sogou` 跳过（它要和搜狗官方渲染图对拍，本质上需要外部基准）。

**而这一改，当场就撞出了一个真 bug**（见下一条）。

**教训**：**一个总是跳过的测试，等于没有这个测试**，但它会给你"我有测试"的错觉。
比没有测试更危险。

### 17. 会在【合法输入】上报错的断言，比没有断言更糟

这条在项目里犯了不止一次，**而且最后一次是在"修测试"的过程中又犯的**。

第一次（校验器）：我加过两条规则，**两条都在完全正常的皮肤上误报** ——
其中"九宫格退化探测"用 26x32 这种**根本不存在的窗口高度**去试，
把两张经过真机验证的正常皮肤判成了退化。
**如果不是当时多看了一眼，我就去改坏它们了。**

```
一条会在正常样本上报错的规则
  -> 会驱使你去"修"本来正确的东西
  -> 比没有这条规则更糟
```

第三次和第四次（写测试时）：我给 `zipdiff` 加了"存在压缩后小于 64 字节的小条目"，
给 `bgcheck` 加了"文字色不能是近黑"。**两条都是我凭空想的，不是真不变量。**

- 前者跑出来 FAIL —— 占位图标压缩后都大于 64 字节，**那本来就不是必须的**；
- 后者跑出来 `pinyin_color=0x000000` —— 但**黑字配浅底完全正常**。
  用户当时抱怨的是【勾边】用了近黑，**我把"勾边色"和"文字色"混成了一件事**。

**落地做法**：每写一条断言，先问"它在**正常输入**上会不会报错？"
会 —— 那它不是断言，是 bug。

### 18. 文档里写着一个不存在的东西，不会报错

README 是我逐字写的，里面 CLI 命令列了 `validate`：

```
node src/cli.js validate <工程目录>
```

**敲下去，它打印帮助然后退出。** 因为 `cli.js` 的 `COMMANDS` 表里根本没有这个命令 ——
README 是照着"应该有什么"写的，代码是照着"当时写了什么"长的。

**这类错误最容易被漏掉，因为它不会报错、只会静默地什么都不做。**

**修法**：我改成**照着文档逐条执行一遍**，而不是照着文档逐条阅读。
一执行，`validate` 不见了、`requirements` 和 `demo` 也漏了，全暴露出来。

**"检查文档"和"执行文档"是两件事** —— 只有后者能发现这类问题。

### 19. 「在我机器上能跑」被当成了「在别人机器上能跑」

测试里硬编码了 `F:/Deepseek_harness/输入法皮肤/...`。我在一个**新建的目录**里
跑了一遍，14 个全过，于是宣布"测试是可移植的"。

**那个结论是错的。** 因为原目录**还在**，测试读得到、写得进。
更糟的是有几处是 `mkdirSync(..., { recursive: true })` ——
在别人机器上要么直接崩（盘不存在），要么**往陌生人的文件系统里创建目录写文件**。

**"干净目录"不等于"干净环境"。** 验证可移植性，必须验证**依赖不存在时**的行为。

### 20. 宣布结论之前先跑验证 —— 我又犯了一次

有一次提交信息我写了"test/ 下已清零"，**紧接着的验证脚本当场打脸**：

```
test/clone.test.mjs:28:  ...F:/Deepseek_harness/输入皮肤/00-原始样本/...
test/overlay.mjs:62:     ...F:/Deepseek_harness/输入法皮肤/06-工作记录/extracted/cn1.bmp
test/overlay.mjs:95:     ...F:/Deepseek_harness/输入法皮肤/04-生成产物/预览图/修图演示.png
```

**还剩 4 处。**

**根因是顺序错了**：我把"验证"和"提交"分成两步、但先写了提交信息。
**如果验证结果先出来，就不会写出那句话。**

**落地做法**：把验证放在**写结论之前**，而不是把结论写完再补一个验证。
这个顺序看起来只是习惯问题，但它决定了你是"知道"还是"以为"。

## 七、这一节的元教训

把上面 16~20 条放在一起看，会发现它们全都是**同一类错误的不同变体**：

```
  验证条件本身没有被验证
```

- 退出码绿了（16）—— 但没验证"测试到底跑了没有"
- 断言 FAIL 了（17）—— 但没验证"这条断言在正常输入上成立吗"
- 文档写了（18）—— 但没验证"照着做能不能成"
- 新目录跑通了（19）—— 但没验证"依赖不存在时会怎样"
- 宣布清零了（20）—— 但没验证"真的清零了吗"

这个项目里**代价最大的几次返工，全都来自这一类**：
不是代码写错了，而是**我用了一个自己没验过的标准去判断对错**。

具体到做法上，只有三条：

1. **任何"通过了"的结论，都要能说清是通过了什么条件得到的**；
2. **条件本身要能被一个具体的、可量化的现象证伪**（"条子高度应从 51 变 80"）；
3. **顺序上，先跑验证，再写结论** —— 哪怕只是一句提交信息。
